建造顺序口径 —— 两侧列表取自生产管线的 extractReplayData().teams[].players[].build_order， 即当前线上同一条链路，未另造数据。原始行的 _kind 只有 unit / recall 两种， 「建筑 / 单位 / 升级」是靠 data.json 名表反查出来的（与线上 itemIsTechUpgrade() 同一判据）。 变形/模式切换类行（*Flying / *Lowered / *Burrowed / 解放者空对地 / 维京突击模式 …） 已按旧链路口径过滤。
时间轴换算 —— build_order.start_time 的单位是 Normal 基准游戏秒（gameLoop / 16）， 而本页时间轴取自统计事件的实际 loop 区间，两者必须换算。换算因子是 按样本实测推导的，不写死 1.4： 本批样本实测 0.715 ~ 1.006。自检判据是「最后一条建造项应落在总时长 90%~100% 处」， 5 个样本实测 92%~100%，全部通过。

口径说明 —— 全部序列取自回放 tracker 流的 SPlayerStatsEvent，即官方客户端回放 overlay （Resources / Income / Spending / Army / Losses）所用的同一张表。原始事件里有 39 个 m_scoreValue* 字段， 这里呈现为 28 个可视图表（少数做了合并或求和，如「军队价值 = 矿 + 气」「支出合计 = 经济+科技+军队」）。 采样密度由录像自身决定（每个样本的实际间隔见其卡片，LotV 下约 7.1 秒）。 人口 已按 1/4096 定点还原；其余为 原始计分值，尚未做单位换算（矿/分、气/分）—— 因此请以 双方对比与趋势 为准，不要直接读绝对值。总时长取生产解析管线的 game_length。
原型边界 —— 本页数据由 prototype/build-datalab.mjs 从 tracker 事件直接导出 （内联 JSON）。正式落地需扩展 js/worker/decoder/replay_data.ts 的统计提取器，其 ReplayDataStatsRow 目前只导出 7 个字段，其余 32 个尚未进入生产管线。
