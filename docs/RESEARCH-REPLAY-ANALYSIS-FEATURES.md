## 0. TL;DR —— 六条判断

1. **官方客户端回放的 9 张 overlay 表就是玩家的心智模型词汇表**。所有竞品都在复用这套词（Resources / Income / Spending / Units / Units Lost / Production / Army / APM）。我们要复用的是**这套词汇**，不是它们的 UI。

2. **竞品分成三类，护城河各不相同**：
   - **托管+跨局聚合类**（SC2ReplayStats、drop.sc、SC2 Tools）→ 护城河是**数据库和历史趋势**，这需要后端。**我们砍掉共享库后，这条路我们不走。**
   - **建造顺序数据库类**（SpawningTool）→ 护城河是**社区贡献的建造库 + 职业对标**。我们无后端也没法做社区库，但**「职业对标」可以用内置静态数据做**（纯客户端）。
   - **单局深度分析类**（starcraft2.ai、SCELight、SC2 Sensei、GuildOrder Replay Coach）→ 这是**唯一不需要后端的品类**，也正是**竞品普遍做得最薄的一层**。我们的主战场在这里。

3. **最大的发现：我们手上的原始事件流比多数竞品用的更深，而且已经解码了。** 实测我们的解码器能拿到镜头轨迹、选择变化、编队操作、指令目标点、科技升级、单位位置分块 —— 竞品里**几乎没有一个产品做「操作与视野」这一层**。这是纯客户端就能兑现的差异化。

4. **官方 `SPlayerStatsEvent` 有 39 个计分字段，我们现在只导出了 7 个。** 剩下 32 个覆盖了官方 overlay 的「Spending 三分法（经济/科技/军队）」「资源余额」「战损/战果」「自伤」—— 也就是说，**官方 overlay 那 8 张表的数据我们其实全都有，只是没取出来用**。这是投入产出比最高的一块。

5. **砍掉共享库 ≠ 砍掉跨局分析。** 「跨用户共享」要后端，但**「我自己的历史趋势」用浏览器本地 `IndexedDB` 就能做**，完全离线、零后端。这一条会让我们的定位从「又一个单局分析页」变成「私人的复盘档案」。

6. **有两件事纯客户端做不到，必须现在就说清楚，不要在设计里假装能做**：
   - **全单位逐帧小地图回放**：录像里**没有地图几何**（地图尺寸、出生点、分矿位置都不在录像文件里），没有底图就画不出小地图。竞品的「等距视图 + 战争迷雾」是**额外自带地图资源**实现的。我们做不到，除非引入地图素材。
   - **任何形式的跨用户聚合、排行榜、对手档案**（SC2 Tools 的"known rematch"、SC2ReplayStats 的联赛追踪）。

## 2. 基准：官方客户端回放的 9 张 overlay 表

这是**唯一不需要调研就会撞上的基准** —— 玩家看了十年的东西。它定义了「录像里能看出什么」这件事的默认答案。

| overlay 表 | 显示内容 | 我们今天有吗 |
| --- | --- | --- |
| **None** | 关闭面板 | — |
| **Resources** | 矿物、气体、人口（供给）计数 | ⚠️ 部分（`minerals_rate`/`vespene_rate` 是**采集速率**不是**余额**；余额字段存在但没导） |
| **Income** | 一段时间内的资源采集量 + 活跃农民数 | ✅ 已导出（`workers` / `*_rate` / `workers_curve`） |
| **Spending** | 资源花在哪：**Economy / Technology / Army** 三类 | ⚠️ 数据存在（39 字段里有），**未导出、未做 UI** |
| **Units** | 单位数量 | ⚠️ 可从 `build_order` + `SUnitBornEvent` 推，未做 |
| **Units Lost** | 损失单位数 | ⚠️ 部分（`workers_lost`/`workers_killed` 只有农民；全军种损失数据在 `SUnitDiedEvent`，未做） |
| **Production** | 当前正在研究/建造/生产的一切 | ⚠️ 可从 `SUnitInitEvent`/`SUnitDoneEvent` 配对算，未做 |
| **Army** | 军队的**资源成本 + 人口** | ⚠️ 部分（`army_minerals`/`army_vespene` 已导出，实测有效） |
| **APM** | 平均与当前 APM | ❌ **完全没导出**（数据源在：`SCmdUpdateTargetPoint/UnitEvent`、`SCmdEvent`、`SSelectionDeltaEvent`、`SControlGroupUpdateEvent`） |

**Spending 三分法的官方口径**（这是社区实测过的，容易搞错）：

| 类别 | 包含 |
| --- | --- |
| **Economy** | 主基地（CC/Nexus/Hatchery）、气矿、补给建筑（Depot/Pylon/Overlord）、农民、Queen |
| **Technology** | 出兵建筑、升级建筑、升级本身 |
| **Army** | 其余一切 |
| 已知缺陷 | **变形类建筑不计入**（Orbital Command / Planetary Fortress / Lair→Hive / Greater Spire），部分建筑（如 Infestation Pit）也不计 —— 官方这个表本身就是有 bug 的 |

> **给设计的直接含义**：如果我们要做「花费结构」页，分类口径必须**照搬这张表**，并且**在 UI 上承认变形建筑不计入**。要么就自己重算一版更准的并明确标注「本站口径」，不能含糊。

## 3. 竞品逐个拆解

### 3.1 SC2ReplayStats（+ drop.sc）—— 「统计最深的老站」

**定位**：录像托管系统 + 长期统计跟踪。

**IA / 功能**（官方文案）：
- **自动上传桌面上传器**（监控录像目录，发现新录像自动传）—— 它的**杀手功能**，把「上传」这件事的成本降到零
- **深度统计**：宣称「比任何其他站都多」——提到「Zealot 的平均存活时长」「Yamato Cannon 用过几次」这类**单兵级细节**
- **训练中心（Training Center）**：自称「市面上唯一的自动教练平台」
- **联赛/段位追踪**：每场后拍对手联赛快照 → 看「我打哪个段位最吃力」
- **种族专属图表**：虫族 **Missed Inject Chart**、人族 **Command Center Energy Chart**（非常有针对性的种族机制指标）
- **地图统计**：按对局类型算最佳/最差地图
- **drop.sc**：它的匿名快传前端 —— 无需注册、超短链接，后端就是 SC2ReplayStats

**对我们的启示**：
- ✅ **「自动发现新录像」是纯客户端也能做一半的**：浏览器可以用 File System Access API（`showDirectoryPicker`）让用户授权一次录像目录，之后每次打开站点自动扫描增量。**这是纯客户端对「桌面自动上传器」的等价物，值得认真考虑。**
- ✅ **单兵级细节**（单位平均寿命、技能使用次数）→ 我们的事件流**完全支持**（`SUnitBornEvent`+`SUnitDiedEvent` 配对、指令流的 `m_abilLink` + 已有 `ability_links.generated.ts` 51KB 能力表）。
- ✅ **种族机制指标**（Missed Inject / CC Energy）→ 数据源我们有基础（`SUnitBornEvent` 时间序列 + 能量值需要 `SUnitEnergy`，**这条未验证**），但「虫族孵化断档」「人族人造卫星能量」这类**机制型指标**是很好的设计思路：**不做泛泛的曲线，做种族机制特有的体检项**。
- ❌ 联赛/段位追踪 → 需要账号体系，**放弃**。

### 3.2 SpawningTool —— 「建造顺序的权威库」

**定位**：建造顺序数据库（社区贡献）+ 职业录像库。

**功能**：按对局类型 / 地图 / 选手 / 补丁 / 标签筛选；从录像中提取建造顺序；多场录像聚合的汇总统计；**职业建造基准对标**（「你的三矿比职业晚了 40 秒」）。

**对我们的启示**：
- ❌ 社区贡献库 → 需要后端，**放弃**。
- ✅ **「职业基准对标」可以纯客户端做**：内置一份静态 JSON（职业选手在常见开局上的关键时间点），把用户录像的时间点和它比。这份数据我们**可以手工/半自动整理**，不占多少体积。**这是砍掉共享库后最值得保留的「对标」能力。**
- ✅ **并列对比**（双方建造顺序带时间戳并列）→ 纯客户端，且我们数据现成。starcraft2.ai 也把它列为核心功能。

### 3.3 starcraft2.ai（SC2 Replay AI Coach）—— 「唯一把 AI 教练做出来的」

**定位**：浏览器上传 → 7 个分析页签 + AI 教练。

**功能清单**（官方 how-it-works 的 8 步流水线，很值得抄结构）：
1. 上传 `.SC2Replay` / `.rep`
2. 解析事件流：资源采集、单位生产、升级、指令、军队移动、死亡、元信息
3. **构造时间轴**：经济/人口/农民/军队价值/编成 系列，按游戏时间索引
4. **建造顺序提取**：带游戏时间戳 + 人口上下文
5. **战斗检测**：从**聚集的单位损失 + 附近军队活动**识别交战；每场给资源损失与交换效率
6. **战术标注**：把可识别模式映射为标签（运营开局 / 时机推进 / All-in / Rush / 骚扰 / 科技转型）
7. **AI 教练**：把结构化数据交给 LLM → 返回锚定到具体事实的建议（**不是通用技巧**）
8. 永久录像页：查看器 + 图表 + 建造顺序 + 战斗列表 + 教练输出

**7 个页签**：总览 / 经济 / 部队 / 战斗 / 建造顺序 / AI 教练 / 战术

**其他关键能力**：
- **等距 3D 渲染 + 单位移动 + 可切换战争迷雾 + 热力图**
- 支持 **Brood War（.rep）** —— 它是极少数还在维护 BW 分析的工具
- **分享一条 URL**（要后端）

**对我们的启示 —— 这是最重要的一个对标物**：
- ✅ 它的**流水线 8 步里，第 2~5 步我们全都能做**（且我们已具备底层能力）。第 6 步「战术标注」= 规则引擎，纯客户端可做。第 7 步「AI 教练」→ **我们有本地 LLM 端点（127.0.0.1:8888，deepseek-v4-flash，512K context），这条我们比它更有优势：数据不出本机。**
- ✅ **「AI 建议必须锚定到具体事实」**这条设计原则要抄死：不给通用技巧，每条建议必须能点回时间轴上的某个时刻。
- ⚠️ **它的等距视图/迷雾/热力图我们没有**（缺地图几何，见 §6.3）。
- ⚠️ 分享 URL → 需要后端，放弃。**替代方案：把分析结果序列化成一个可下载的自包含 HTML 文件**（纯客户端，零后端，效果接近）。**这个想法值得单独评估。**

### 3.4 SC2 Tools（sc2tools.com）—— 「云 + 桌面 + 直播」的全家桶

**定位**：天梯玩家的完整伴侣（分析 + 练习 + 直播）。

**功能**：
- 桌面 App 自动读录像 → 重建对局
- **对手档案（opponent dossier）**：别名/小号/条码名归一 → 重赛时知道对面偏好什么开局、历史战绩
- **建造 playbook**：把任意录像存为可复用建造，定义关键节点；历史录像后台重新分类
- **Replay Theatre**：真地图上的 3D 重构（单位、迷雾、**精确技能释放**、贴地路径、生产轨道、音乐、全屏）
- **OBS 直播叠加**：30+ 组件一个 URL，做成 Browser Source
- **Player Intelligence**：胜率周趋势、MMR 曲线、最擅长的对局/地图、建造组合分布、**技能指纹**（"Adaptive Timing Specialist"）、建造库有效数、对局边缘值
- **私人录像库**：原始文件归档 + 下载；**VOD 跳转**（Twitch/YouTube 按时间戳跳）
- 筛选器贯穿所有图表（时长/地图/对局/建造/MMR 段）

**对我们的启示**：
- ❌ 对手档案 / 跨局 MMR / 云同步 / OBS → 全要后端，**放弃**。
- ✅ **「筛选器贯穿所有图表」这个 UX 范式要抄**：条件设一次，所有图跟着变，不要在页面之间重置。
- ✅ **「技能指纹」式的一句话画像**（不是统计数字，是给玩家一个可复述的自我描述）→ 纯客户端规则引擎可做，**是很讨喜的输出形态**。
- ⚠️ Replay Theatre 需要地图资源，放弃。

### 3.5 SCELight / Sc2gears —— 「本地桌面的极客路线」

**定位**：Java 桌面工具（跨平台），Sc2gears 的后继。捐赠解锁全部功能。

**功能**：APM、**事件序列**、建造顺序、地图信息、**聊天记录**、折线图与地图可视化、**多录像分析器（Multi-Replay Analyzer）** —— 跨大量录像算种族/对局类型统计、胜率、日历式对局摘要。

**对我们的启示**：
- ✅ **它是唯一「纯本地、不上传」的成熟先例** —— 说明这条路的用户是存在的（而且现在只剩 Java 桌面，Web 上一片空白）。**这是我们的最大定位机会：Web 版的 SCELight。**
- ✅ **「事件序列」视图**（把整局的原始事件按时间列出来）→ 极客向，但很适合作为「我用证据支撑结论」的那个页签。我们事件最多 2 万条，能做得比它好。
- ⚠️ **多录像分析**（跨局）→ 它靠本地文件夹，我们靠 IndexedDB，可以做，见 §7。

### 3.6 SC2 Sensei（sc2sensei.top）

Web 应用，图表可视化 + 对局拆解 + 提升工具。社区索引对它的描述很简短，**我没有实测**，只能确认它属于「不需要后端的单局分析」品类。**不引用它的具体功能。**

### 3.7 GuildOrder Replay Coach —— 「诊断列表」的 UX 范式（2026-07 更新，很新）

**定位**：公会插件，把录像变成一次教练课。支持 SC2 + AoE2。

**功能与 UX**：
- 拖入文件 → 服务端几秒解析（**内存解析后丢弃原始文件**，只留分析）
- 每位玩家一张卡：胜负、APM、宏观数值的 stat bars、收入与农民趋势、建造顺序时间轴
- **核心输出是「发现列表（findings）」**：确定性规则把数字变成建议，**按严重度排序**，每条打 `major` / `minor` / `info` 标签，且**每条都带确切数字**
  - 例子：「**补给卡了 12% 的对局时长**」「Feudal 在 12:25」「spending quotient 74」「15 分钟的对局只有 38 个农民」
- 产品叙事：「先修 major，下周再传一次，看它消失」→ **把 findings 列表变成进度条**

**对我们的启示 —— 这是本次调研里最有价值的 UX 发现**：
- ✅ **「按严重度排序的发现列表」比一堆曲线更有用**。曲线是证据，findings 是结论。**我们的页面必须两者都有，且 findings 在前。**
- ✅ **`major / minor / info` 三级严重度 + 每条带确切数字** → 直接抄。
- ✅ **「修掉 major，下次再看它消不消失」** → 这是把「单局分析」变成「训练闭环」的钩子。**配合 IndexedDB 本地历史，我们可以做这个闭环，而且不用后端。**
- ✅ 它支持多游戏（SC2+AoE2）说明**解析层与展示层解耦**是这个品类的架构共识。

### 3.8 已经死掉的（教训比活着的重要）

| 产品 | 死亡时间 | 它有什么 | 教训 |
| --- | --- | --- | --- |
| **ggTracker** | 2018-01 | **交互式图表：军队强度、编成、单位位置**；APM / 胜率 / **Spending Skill** 图表 | 「Spending Skill」这个指标本身很有价值，但**托管型站点的运营成本吃掉了它** |
| **gggreplays** | 2023-02 | 承接 ggtracker 代码库 | 代码库能继承，**用户和运营成本不能** |
| **SC2 Pulse** | 现役但**不做录像分析** | 只做天梯 MMR | 单做「统计数字」不构成差异化 |

**教训**：
1. **托管 + 长期运营是这个品类的死亡原因**。凡是把价值押在「服务器上的历史数据」的产品，都在维护成本面前倒下。**我们砍掉共享库，反而规避了这个品类的头号死因。**
2. **「Spending Skill」（花费效率）是个被验证过有价值、但随产品一起消失的指标** → 我们的 39 字段里有完整的经济/科技/军队花费数据，**可以把它做回来**。
3. 「单位位置」有人做过、死了，不代表方向错，但**它的成本（地图资源+渲染）与收益不成正比** → 不做。

## 5. 归纳：一个录像分析工具的「功能全集」

把上面所有竞品摊平，功能可以归成 8 层。**层与层之间是依赖关系，不是并列关系** —— L0 塌了，上面全废。

```
L7 诊断与教练       「我该改什么」          ← 竞品最薄、用户最想要
L6 操作与视野       「我怎么操作的」        ← 全行业空白，我们独有
L5 单位级细节       「具体谁死了/活了多久」
L4 战斗与交换       「这几波谁赚了」
L3 建造与科技顺序   「我什么时候做了什么」
L2 宏观三线         「经济/科技/军队」      ← 官方 overlay 的核心
L1 对局元信息       「这是哪一局」
L0 时间轴 + 状态同步 「把它连起来」          ← 一切的地基
```

| 层 | 输入（我方数据源） | 输出（用户看到什么） | 竞品覆盖度 | 我方就绪度 |
| --- | --- | --- | --- | --- |
| **L0 时间轴** | `game_length` + 所有事件帧 | **一根可拖动的全局游标**：拖动它，所有图表/表格/读数同步。**这是我们现有 UI 最缺的东西。** | 全员都有，但多数是「滚动页面」而非「同步游标」 | ⚠️ 数据够，交互要重做 |
| **L1 元信息** | `map_name`/`game_length`/`winner`/`region`/`client_version`/`start_time`/`chat` | 对局头：地图、时长、版本、时间、胜负、玩家（名字/种族/颜色） | ● | ✅ 已有 |
| **L2 宏观三线** | `SPlayerStatsEvent` 39 字段 + `workers_curve` | 农民数、**收入速率**、**资源余额**、**Spending 三分**、军队价值、人口/上限 + **卡人口区间高亮** | ● | ⚠️ 39 字段里只导了 7 个 |
| **L3 建造与科技** | `build_order`(`SUnitInit/Done/Born/TypeChange/Upgrade`) + `ability_links` | 双方并列的建造时间轴；**分建筑/单位/科技/变形四类**；关键节点自动标注（首兵、二矿、科技转型） | ● | ✅ 数据已有（⚠️ 见 §6.2 的分类缺口） |
| **L4 战斗与交换** | `SUnitDiedEvent`(带击杀者) + `SUnitInitEvent` 配对成本 | **自动识别交战**：时间聚集 + 参战单位 → 每波给「损失资源 / 击杀资源 / 交换比」 | 只有 starcraft2.ai 声称做了 | ⚠️ 需自研聚类规则 |
| **L5 单位级** | `SUnitBorn`+`SUnitDied` 配对、`SCmdUpdateTargetUnitEvent`+`ability_links` | 编成随时间的堆叠图；单位平均存活时长；技能/能力使用次数 | SC2ReplayStats 宣称做了 | ⚠️ 需新增组装 |
| **L6 操作与视野** | `SControlGroupUpdateEvent`(5946!)、`SSelectionDeltaEvent`(2247)、`SCameraUpdateEvent`(4840)、`SCmdUpdate*` | **编队习惯**（用了几个编队/什么时候设的）、**选择行为**、**镜头活动热力**（在哪些区域停留多久）、**APM/EPM 曲线** | **全行业空白** | ⚠️ 数据丰富，**零组装** |
| **L7 诊断与教练** | L2–L6 的派生指标 | **按严重度排序的发现列表**（`major`/`minor`/`info`，每条带确切数字 + 跳转到时间轴的时刻）+ 本地 LLM 的针对性点评 | GuildOrder 做了列表；starcraft2.ai 做了 AI | ⚠️ 规则引擎 + LLM 接入都是新工作 |

### 5.1 从这 8 层推出的三条设计原则

1. **L0 优先于一切。** 现在我们的页面是「一堆独立的卡片」。竞品里最好用的都是「一根时间轴 + 所有东西挂在上面」。**重设计的第一决定就是：把时间轴提升为主控，而不是一个卡片。**

2. **L7 必须在首屏，不能塞在最后。** 玩家的真实问题是「我为什么输」，不是「给我看看曲线」。曲线是**证据**，findings 是**答案**。GuildOrder 的做法（先列 3 条 major，每条带数字和修法）应该成为我们的首屏形态。

3. **L6 是我们的差异化主战场。** 全行业空白 + 我们数据最丰富 + 纯客户端就能做。**但要注意：它是最容易做成「好看但没用」的一层。** 必须落成具体结论（「你的第 3 个编队全程没用过」「23–27 分钟你 71% 的时间镜头在自己主矿」），而不是又一组曲线。

### 6.2 已确认的 4 个数据层问题（必须在设计前决定怎么处理）

**① `SPlayerStatsEvent` 有 39 个字段，我们只导出了 7 个。**

实测 39 个字段全部真实存在。按「是否至少出现过一次非零值」分类：

| 组 | 字段 | 实测有值？ |
| --- | --- | --- |
| 人口 | `FoodUsed` / `FoodMade` | **恒有** |
| 农民 | `WorkersActiveCount` | **恒有** |
| 资源余额 | `MineralsCurrent` / `VespeneCurrent` | **恒有**（气体局中后期才有值属正常） |
| 采集速率 | `MineralsCollectionRate` / `VespeneCollectionRate` | **恒有** |
| **Spending 三分 · 当前存量** | `MineralsUsedCurrentEconomy/Technology/Army`（+ 气体三件） | **有**（Economy 恒有，Technology/Army 随局势出现） |
| **Spending 三分 · 建造中** | `MineralsUsedInProgressEconomy/Technology/Army`（+ 气体三件） | **有** |
| **Spending 三分 · 损失** | `MineralsLostEconomy/Technology/Army`（+ 气体三件） | **有，稀疏**（只在真发生时非零 —— 这是正确的行为） |
| **Spending 三分 · 战果** | `MineralsKilledEconomy/Technology/Army`（+ 气体三件） | **有，稀疏** |
| 活跃兵力 | `MineralsUsedActiveForces` / `VespeneUsedActiveForces` | **有**（⚠️ 与 `UsedCurrentArmy` **不等价**，见下方第 2 条更正） |
| **自伤** | `*FriendlyFire*`（12 个字段） | **可用，但取决于是否真发生**（详见下方更正） |

> 🔴 **更正（我第一版写错了，已实测推翻）**：自伤字段**不是恒为 0**。
> 逐字段实测（5 个样本）：
> - `CN_ZVP` / `CN_PVT`：全 0（这两局没发生自伤）
> - `US_TVP`：8/1746 非零（零星）
> - `US_TVR(T)_2018_old`（HotS 老录像）：`MineralsFriendlyFireTechnology` **166/491 非零**（最大 50）、`VespeneFriendlyFireTechnology` **166/491 非零**（最大 25）
> - `hero`（职业 PVZ）：`MineralsFriendlyFireEconomy` **207/265 非零**（最大 725）、`MineralsFriendlyFireArmy` 85/265、`MineralsFriendlyFireTechnology` 79/265、`VespeneFriendlyFireArmy` 45/265
>
> **所以自伤统计是真的工作的**（Zerg 毒爆/自爆、取消建造这类的自伤都会被记）。
> 但它在**短局里全是 0** —— 意味着：**不能把自伤做成常驻指标**，只能作为「本局若发生才出现的发现项」。

> 🔴 **更正（第二条，同样被实测推翻）**：`MineralsUsedActiveForces` 与 `MineralsUsedCurrentArmy`
> **并非等价**。实测 4/5 样本逐条相等，但 **`hero` 局有 74/265 条不等**
> （例：`ActiveForces=2275` vs `CurrentArmy=2175`，差值恒为 100）。
> → **不能当同一个指标处理**，语义未确认，暂不使用其一。

**② 官方统计的采样粒度是「每 10 秒」，不是每秒。**

实测 `SPlayerStatsEvent` 的采样帧：`1, 1, 160, 160, 320, 320, 480, 480, 640, 640, 800, 800…`
→ 每 **160 gameloop** 采一次 = **10 秒**（Normal 基准），且每次同帧两位玩家各一条（所以帧号成对出现）。

**这意味着**：官方 overlay 的曲线本身就是 10 秒粒度的，**「精确到秒的收入曲线」在数据源层面不存在**。而我们的 `workers_curve` 是**逐秒前向填充**的 —— 那是**插值出来的平滑**，不是真实采样。

> **设计含义**：不要在 UI 上宣称「逐秒精确」。曲线必须**标出真实采样点**，或者明确说明「10 秒采样 + 线性插值」。这条如果不写清楚，会变成下一个「28:58 vs 40:34」式的口径事故。

**③ 时间单位不一致（两套口径混用，是历史包袱）。**

| 字段 | 单位 | 证据 |
| --- | --- | --- |
| `build_order[].start_time`、`worker_deaths[].time`、`chat[].time` | **秒**（`gameloop >> 4`，16 loops/秒） | 实测值均为整数秒（1, 18, 24…） |
| `workers_curve[].t` | **分钟**（`秒 / 60.0`） | 源码确认 + 实测：US_TVP 末点 `17.05` vs `game_length 1026s / 60 = 17.1` |
| `stats[].minute` | **分钟序号（1-based）** | `pyInt(dsec / 60) + 1`，且 `dsec = (gameloop/16)/1.4` |
| `game_length` | **秒**（但 LotV 下被除以过 1.4，见项目备忘） | — |

> **设计含义**：**前端必须在一个地方做单位归一，不能各处自己换算。** 建议新增一个统一的 `toGameSeconds()` / `formatTime()` 出口，所有页面只走它。

**④ `build_order` 目前不区分「建筑 / 单位 / 升级」，全都塞进 `_kind: "unit"`。**

实测 5 个样本的 `build_order` 条目 `_kind` **只有 `"unit"` 一种**（另有独立的 `"recall"` 行）。`SUpgradeEvent` 在内部是走 `fromEvent: "upgrade"` 的，但输出时被映射成了 `_kind: "unit"`。

> **设计含义**：**L3 层的「分建筑/单位/科技/变形四类」现在做不到，需要先改组装层**（在 `_kind` 上补出分类，或在行上加 `category` 字段）。这是设计前必须排期的一项。

### 6.4 位置事件的实测细节（供后续 POC 参考）

- **坐标编码**：`m_items` 是扁平数组，**每 3 个数字描述 1 个单位**（长度必为 3 的倍数）。
  实测一段：`0, 93, 100, 24, 74, 84, 19, 75, 84, 97, 75, 83` → 4 个单位。
- **首个数字是标志位**，实测取值集合含 `0` 与大量非零值（最大到 356）。
- **`m_firstUnitIndex` 逐事件变化且大致递增**：`21, 43, 44, 51, 61, 65, 77, 91, 95, 183, 199, 201, 208, 213, 221…`
  → **分块/滚动上报语义，不是全量快照**。这是判定「能不能做小地图」的关键，**不要误当成快照直接用**。
- **上报频率**：实测相邻事件间隔 240 gameloop = **15 秒**（US_TVP 首次在 gameloop 1920 才开始有）。
- **单位数随时间增长**：US_TVP 前 20 个事件 1~17 个单位，后 5 个 26~44 个单位 —— 与军队成型一致，说明它跟踪的确实是活跃单位。
- **总量**：US_TVP 66 个事件 / 3276 个数字 = 1092 个单位位置点；hero 局 65 事件 / 3186 数字。

## 7. 差距分析与机会点

### 7.1 我们的结构性优势

| 优势 | 为什么竞品没有 |
| --- | --- |
| **纯客户端**（不上传、不注册、离线可用、数据不出本机） | 现役产品里只有 SCELight（Java 桌面）。**Web 端是空白。** |
| **原始事件流最深且已解码** | 多数竞品只取经济/建造；镜头、编队、选择这一层**没人做** |
| **本地 LLM 端点**（127.0.0.1:8888，512K context） | 竞品的 AI 教练要把数据传到服务器（含付费）；**我们能把「数据不出本机」当卖点** |
| **中文优先** | 国内只有 `sc2.replays.net`（纯录像库，无分析） |
| **WASM 性能**（70 万事件/秒） | 纯客户端做 2 万事件的分析不卡，桌面级体验 |
| **本地批量**（现有的录像列表侧边栏） | 无需上传就能处理一整个录像文件夹 |

### 7.2 三个高价值机会点

**机会 1：L6「操作与视野」—— 全行业空白层**
竞品矩阵这一行**全员为空**。我们的数据量最大（US_TVP 编队事件 5946 条）。可落成的具体指标举例：
- 编队使用谱：设了哪几个编队、各自的设置时刻、**哪个编队设了从没用过**
- 镜头活动：各区域的驻留时长占比、切屏频率、**「你有 40 秒没看主矿」**
- 选择行为：平均选择规模、是否长期保持编队、**「每次交战后重建编队的平均耗时」**
- APM/EPM 曲线 + **有效操作率**（指令数 vs 选择数）

**机会 2：把「跨局」用 IndexedDB 做回来（不违反纯客户端）**
砍掉共享库砍掉的是「跨用户」，不是「跨局」。用 `IndexedDB` 存每条录像的派生指标：
- 我的历史趋势（胜率、卡人口率、Spending 结构随时间的漂移）
- 「上周的 major 这周消失了吗」→ **GuildOrder 的闭环叙事，纯本地版**
- 用 File System Access API 记住录像目录 → 每次打开自动发现新录像 → **SC2ReplayStats 桌面自动上传器的纯客户端等价物**
- ⚠️ 需确认：`IndexedDB` 存储配额、以及是否需要「一键清除本地数据」的隐私开关

**机会 3：39 字段里的 Spending 三分法 = 官方 overlay 的复刻**
数据全在、口径有公开定义（§2）、只导出了 7/39。**这是投入最小、看起来最完整的一块。** 并且可以顺带把 ggtracker 那个消失的 **Spending Skill** 指标捡回来。

### 7.3 明确放弃的

社区建造库、分享链接、对手档案、MMR/段位、直播叠加、VOD 跳转、小地图/等距视图、4K 渲染。

## 8. 建议的功能清单（按优先级）

### P0 —— 地基（不做这些，上面全废）

1. **全局时间轴主控**：一根可拖动的游标，所有面板同步；所有图表垂直对齐到同一根时间轴。
2. **单位归一 + 格式化出口**（`gameSeconds` / `mmss` / 百分比），全站只走一处 —— 修掉 §6.2③ 的单位不一致。
3. **对局头**（地图/时长/版本/时间/胜负/双方玩家卡片）。
4. **双方并列的建造顺序时间轴**（已有数据，只差 UI）。

### P1 —— 首屏价值（决定用户会不会留下来）

5. **诊断发现列表**（`major`/`minor`/`info`，每条带确切数字 + 点击跳转时间轴）—— **首屏第一块**。
6. **宏观三线**：农民数、收入速率、**资源余额**、**Spending 三分（经济/科技/军队）**、军队价值、人口/上限 + **卡人口区间高亮**。
7. **APM/EPM 曲线**（数据已在，需组装）。

### P2 —— 差异化（竞品空白，我们的护城河）

8. **操作与视野页**：编队使用谱、镜头活动分布、选择行为、有效操作率。
9. **战斗与交换**：自动识别交战，每波给损失/战果/交换比；工人骚扰战损热区（`worker_deaths` 已带击杀者）。
10. **单位级细节**：编成堆叠图、单位平均存活时长、技能使用次数。

### P3 —— 训练闭环

11. **本地历史**（IndexedDB）：跨局趋势 + 「上次的 major 修掉了吗」。
12. **录像目录授权 + 自动发现新录像**（File System Access API）。
13. **本地 LLM 教练**：把 P1/P2 的派生指标喂给本地模型，输出锚定到时间轴的建议。

## 9. 待探宝拍板的决策点

1. **确认「砍掉共享库」的边界**：我理解 = 砍掉「跨用户共享/账号/上传」。**但「本地 IndexedDB 跨局历史」我建议保留**（机会 2）。要保留吗？
2. **L6「操作与视野」是否作为主差异化方向**？它全行业空白，但要新写组装层 + 需要设计上把它落成结论而不是曲线。
3. **AI 教练是否现在做**？本地端点已就绪（数据不出本机是卖点），但要先有 P1 的派生指标喂它。
4. **小地图确认放弃**？我的结论是「缺地图几何 → 做不到」，除非愿意引入地图素材包。
5. **官方 overlay 的 9 张表口径照搬，还是自研并标注「本站口径」**？照搬的好处是玩家零学习成本；自研的好处是能修掉官方那些已知 bug（变形建筑不计入）。
